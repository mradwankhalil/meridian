## Findings requiring correction

1. **P1, #1396: arbitrary system instructions disappear from lineage.** `src/proxy/adapters/claudecode.ts:367–368` truncates every system-turn content array after its last `cache_control` breakpoint. Cache-prefix metadata does not prove the suffix is request-scoped. Requests `[cached stable prefix, durable instruction A]` and `[cached stable prefix, durable instruction B]` canonicalize identically; the altered earlier history can resume an SDK session that never received B. This violates the architecture's edited-history/fresh-replay contract. The PR acknowledges this as an unobserved limitation, and the new test at `claude-code-system-turn-lineage.test.ts:67` deliberately asserts that unknown suffix wording is discarded. Narrow to the exact observed batching reminder; preserve all unknown post-breakpoint blocks. Replace that test with durable-tail preservation plus an HTTP modified-history/divergence control. Keep current reminder-only tail handling and UUID-index fixes. The observed exact client shape is documented in the fixture test and committed scripted harness: cached `<total_tokens>N tokens left</total_tokens>` followed by the exact English batching reminder; the next request retains token text and drops only that reminder.

2. **P2, #1400: pool wait can contradict effective remaining benches.** `src/proxy/server.ts:1668–1676` marks exhaustion monotonically but returns the newly calculated `until`, even if an earlier/larger account or model mark remains. `poolEarliestReset` at `1688–1699` starts with this possibly smaller `earliest`, then only lowers it while inspecting effective benches. Reattempting the active/retained account when the pool is exhausted can therefore advertise 10 minutes while every effective account+model bench is at least 3 hours. Derive the wait from effective `benchedUntil` after all marks; do not seed the pool with an obsolete smaller attempted mark. Add both repeated-shorter-mark and overlapping account/model controls through JSON and SSE paths, plus the retained-account-only case. The existing tracker tests prove max(account, model), but the pool tests do not join that invariant to retry calculation.

3. **P2, #1399: stop during an existing background sweep retains 64 deletions.** `server.ts:903` returns `sessionGcRunning` before the drain cap at `909–912` can apply. `sessionLifecycle.ts:826` captures the limit once. If an idle proxy closes during a normal sweep, HTTP drain exits immediately because no requests are active, then close awaits the remaining 64-deletion sweep. Contributor large-store measurements put this at roughly 26–31 seconds vs the old 16-delete sweep near 10 seconds. The new close test explicitly waits for startup GC first and misses this interleaving. The PR discloses pre-drain sweeps remaining at full cap, but the claim that stopping costs no more than before is false for idle stop. Add a paused-deletion/start-close test and reduce remaining work cooperatively between joined deletions; never abandon a deletion or durable transaction. Full details and exact test references are in the secondary report.
